# Analytics implementation handoff - October 19, 2026

Branch: `codex/analytics-remaining-implementation`, based on the merged PR #607.
This is an implementation checkpoint, not a production-readiness acceptance.
The user selected finishing/hardening the existing analytics features, excluding
the codebase-wide tenancy migration in the original scope report.

## Implemented in this checkpoint

- Governed dispute rate, refund rate, and main-app payout failure count; the
  registry now has 16 metrics and 14 non-restaurant metrics are alertable.
- Underlying-record evidence and canonical summaries for all 16 builder
  metrics, with read-only repeatable-read snapshots, pagination, capped exports,
  audit event types, and personal query history filtered by current grants.
- Alert observations/history, previous-period percentage comparisons for the
  three new operational metrics, category preferences, independent delivery
  channels, per-rule worker locking, and durable SMS delivery claims.
- Business Hub invoice-revenue analytics: paid invoices only, separate currency
  accounts, exact monetary strings, monthly series and paginated source invoices.
  Expenses are excluded because they have no recorded currency.
- Paid-order restaurant retention cohorts and currency-separated top items;
  featured-placement conversion deduplication and seven-day identified-user
  click attribution, excluding unpaid/cancelled/refunded orders.
- Natural-language business/restaurant filter-name correction, parse-attempt
  auditing, and an optional validated JSON-only model fallback through the
  existing provider. `ANALYTICS_NL_MODEL_ENABLED` must explicitly be `true` and
  the provider configured; this path was not enabled against a live provider.
- Matching legacy/namespaced translations in en/es/fr/ht/ar, responsive query
  and alert controls, browser regressions, and refreshed Business Hub SOP assets.

Migrations 893-897 are additive. They were exercised through the real migration
runner against a disposable database only; production was not migrated.

## Still needs finishing before release

1. **Verification gate:** finish the final-tree backend/client/browser checks,
   diagnose every explicit failure, and obtain green remote CI, including the
   migration rehearsal. Repeat the authenticated admin/business flows and test
   denied/revoked grants with real sessions. Do not enable or merge solely on
   the earlier focused test counts.
2. **SMS crash recovery:** claims prevent resending the same delivery key, but
   a new cooldown bucket creates a new key. An uncertain/interrupted send can
   therefore be attempted again in a later bucket. Add an explicit unresolved
   claim/reconciliation policy across buckets and test crashes at boundaries.
   Email-only digest preferences currently suppress realtime delivery without
   inserting an in-app row; add a dedicated digest queue if digest delivery is
   required for this channel combination. Live email/SMS/push remain unverified.
3. **Query navigation hardening:** exercise slow requests, language/meta changes,
   browser back/forward and account switches. The restored-query effect aborts
   on dependency changes but retains its last-request marker; ensure an aborted
   request can be retried. The new browser fixture's translation helper also
   needs interpolation support and stronger keyboard/history assertions.
4. **Consumer parity and drill links:** the builder provides evidence, but not
   every MoneyPage, support, operations or Customer 360 KPI/timeline item has
   been wired to it. Add links only after proving the source KPI and evidence
   share the same window, currency, denominator and permission semantics.
5. **Campaign breadth:** this implementation covers featured placements, not a
   general broadcast/open/delivery/promo/referral reporting platform. Anonymous
   clicks cannot be tied to paid orders, historical events cannot establish
   missing attribution, and best-effort event writes can still be lost (now
   logged). Reliable delivery/backfill and broader campaign types remain work.
6. **Governance/operations:** legacy daily-performance snapshot endpoints are
   marked deprecated/unmaintained, not rebuilt or removed. Assign retention and
   cleanup ownership for alert observations/audit history. Review existing alert
   rules affected by period-default changes. Update stale historical progress
   claims and worker/campaign comments before operational acceptance.
7. **Activation:** review/apply migrations 893-897 through the deployment
   workflow, verify worker readiness and live channel preferences, and keep the
   optional model fallback disabled until provider/privacy/acceptance checks
   pass. The model receives questions and permitted catalog metadata, not SQL or
   database results; free-text questions still need a privacy review.

## Explicitly outside this pass

Automatic row-level enforcement across hundreds of controllers, full One Truth
scale/analyst-scope redesign, and broader logistics/business tenancy convergence
are separate architectural work. Existing permission checks must remain in
place; this branch does not claim codebase-wide automatic row security. Likewise,
invoice revenue is not a complete business profit-and-loss implementation, and
the payout failure metric does not combine unrelated payout products.
