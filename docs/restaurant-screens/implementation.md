# Restaurant screen control center and synchronization

Browser-first delivery for POS unpaid capture, self-order kiosk, kitchen stations, expediting, pickup displays and customer tracking. Legacy guest tracking links are resolved without accepting marked stored hashes as bearer tokens. No LAN hub, payment hardware, self-approval, authorization bypass or automatic financial replay.

## Rollout and rollback

Migration 884 was initially free at `951b3a1e`. After newer default-branch work claimed 884–886, this change was renumbered **887** against fresh `origin/old-files-claude` (`9f0057d3`); no open pull requests claimed 887. It adds `food_restaurants.screens_v2_enabled`, default **false**, the journal/outbox, revisions, device acknowledgement fields and unpaid draft storage. The standard migration runner applies it.

Authorized restaurant managers open **Home / Operations → Open control center**, enable managed screens for that restaurant, and pair each browser with a one-use 15-minute code. No deployment secret or financial processing flag is added. Existing device tokens remain scoped to restaurant, application and assigned location; they are never placed in URLs. Payments, refunds and shifts continue through existing authenticated staff flows. A paired POS screen captures unpaid counter drafts; **Open POS** uses the existing staff POS for shift/payment work.

New entry: `/restaurants/screens/:restaurantId/:screenRole` (`control`, `pair`, `pos`, `kiosk`, `kitchen`, `expeditor`, `queue`). Legacy POS/kitchen/kiosk/queue and native endpoints remain available. Preview is read-only. New labels have matching English, Spanish, French, Haitian Creole and Arabic legacy/common catalogs.

To roll back, disable managed screens in the control center. Production actions on managed devices stop after the new state is received; server gates also enforce the flag. Journal disabling publishes a final invalidation. Existing routes and authenticated unpaid draft review/import remain available. Historical orders with no recorded location stay in Default store; no location is guessed or backfilled. Finish that legacy work there before switching devices to another location. Do not clear browser storage with unresolved work. An operator can recover drafts from old device/location scopes on that same browser after management authorization. Legacy browser kiosks now also retain offline drafts in IndexedDB for staff review instead of automatically sending them into production. Older local records are retained and shown for reconciliation; financial diagnostics are never treated as payment instructions. Disabling this feature does not disable legacy/native applications.

## Consistency and recovery contracts

- Database row triggers append invalidations in the same transaction as order/item/modifier, menu, restaurant, inventory availability, runner, station and device configuration changes. A locked restaurant stream row allocates serialized revisions; rolled-back transactions cannot consume a committed cursor. Moving an order invalidates both old and new locations. No order description or recorded price is rewritten from the menu.
- Repeatable-read snapshots contain a consistent cursor and paginate 250 operational orders. A changed snapshot page requests restart. Change feeds scan before location filtering, return a resumable cursor and demand a fresh snapshot after pruned history or a reset. Kiosk and pickup device feeds expose revision invalidations only; operational order data requires staff, POS or kitchen device permissions. Pickup snapshots contain queue numbers only.
- The publication outbox retries failures and emits only redacted restaurant/revision notifications. Socket delivery is a wakeup, not an accounting or ordering authority. REST catch-up runs after reconnect, with five-second polling fallback. Published journal records are retained seven days; unpublished records are not pruned.
- A ref-counted browser sync client serializes catch-up, deduplicates wakeups, aborts stopped requests, ignores earlier account/scope responses, and advances its applied cursor only after a replacement snapshot succeeds. Heartbeats run every 15 seconds; connection is degraded at 45 seconds and offline at 60 seconds. Data freshness and configuration acknowledgement are separate indicators.
- Configuration remains pending until acknowledged. Disruptive changes wait for the kiosk guest session to end and unresolved local operations to be addressed. Assignment/location changes re-enter the new managed route safely.
- IndexedDB isolates cache and operations by restaurant, device/location or signed-in staff account. Stable UUIDs and a cross-tab Web Lock (renewed IndexedDB lease fallback) prevent duplicate replay. Online unpaid requests are staged durably before submission, so a browser restart or lost response can recover the original UUID. Successful unpaid payloads are stripped of guest details locally.
- Offline import creates a durable **unpaid draft**, never a production order. Authorized staff obtains a current itemized quote, explicitly approves it, then the existing order creation transaction validates menu, modifiers, stock, availability, ordering state, permissions, prices and the reviewed menu fingerprint. A change after review conflicts. Repeated acceptance or an ambiguous original online response returns/links the same order.
- Kitchen operations carry expected entity revisions and idempotency keys. Conflicts include current revision/state. Station devices can complete their assigned items; only expediting can publish whole-order readiness after existing item/quality gates. Pickup completion uses the established payment, inventory and completion handler; delivery handoff remains in the runner flow. No financial operation exists in the new offline queue.
- Kiosks reset cart/name/confirmation state after inactivity and between guests. Delayed submission results cannot populate a later guest session. Background recovery never displays another guest's confirmation or tracking token.

During a store-wide internet outage, devices retain their own local work but **cannot exchange new work with other screens until connectivity returns**. Provisional references are not confirmed queue numbers.

## Verification evidence

Local checks use synthetic accounts, devices, meals and credentials, not production money or customer records.

- `server/__tests__/restaurantScreenSync.test.js`: scope/cursor validation, heartbeat thresholds, location filtering and retained-history reset.
- Existing restaurant app-flow and food-order regressions, plus background-worker lifecycle checks.
- `server/scripts/verify-restaurant-screen-sync.cjs`: guarded to a loopback disposable `oxsteed_rehearsal` database. Real PostgreSQL tests cover rollback/commit ordering, 300 active orders over snapshot pagination, location isolation and old-location invalidation, scoped public output, unauthorized access, offline import/idempotency, reviewed price conflict, ambiguous online-response recovery, expected revisions, item preparation → expeditor quality → paid pickup, revoked credentials, outbox failure/retry, feature rollback and retained unpaid recovery.
- `client/scripts/restaurantScreens.browser-check.cjs`: real browser with synthetic APIs; control center pairing/review, station/expeditor workflow, kiosk offline capture and guest isolation, IndexedDB reload and browser-profile restart, two-tab duplicate prevention, financial-queue rejection, snapshot pagination/retry, stopped-response isolation, expired authorization, 120 responsive theme/locale layouts (320, 390, 768, 1360 and 1600px, plus mobile kiosk checkout), and fullscreen fallback. It is included in the existing CI browser-check glob; also runnable as `npm --prefix client run test:restaurant-screens`.
- Measured synthetic catch-up: 1,000 committed journal changes in **0.3–2.1 seconds** locally, under the 15-second target. Browser fixture with 20ms change-feed and 40ms snapshot delays measured healthy wakeup p95 about **65ms** and missing-socket polling about **3.6s**, under 2s/10s respectively. These are deterministic component/database measurements on this local macOS/Colima setup, not a production end-to-end latency certification or a physical store network test.
- Updated visual guide: **Connect restaurant screens and recover offline work**, with desktop/mobile synthetic screenshots, printable download and restaurant handbook. Related setup/preparation/staff guides link to it. PDF checks rendered 187 pages across the four affected guides and restaurant handbook with no detected page overflow; representative guide pages were visually inspected.
