1. **The double-prefix /api URL bug class is systemic.** Pass 1 found it in the work-agreements pages, pass 2 in the merchant Refund/Split/Merge buttons, pass 3 confirms it persists with a new variant (caller-supplied attachment URLs laundered through /api/storage/).

9. **Notification silence on money.** No payment_failed email eligibility, no refund notifications of any kind, dispute lifecycle notifies nobody or one side, verification decisions silent, subscription emails have zero emitters.
10. **Stuck states with no exit.** Accepted-forever jobs, pending_signatures-forever agreements, scheduled-forever bookings, open-forever tickets and chat payment requests, pending-forever settlement queues in single-admin orgs, undecidable maker-checker queues.
11. **Duplicate systems that diverge.** Two agreement systems, two quote systems, two listing toggles, three generations of identity flags, 16 of 17 seeded DB flags as dead theater with contradictory duplicates.
12. **Settings and notification preferences are largely theater.** Dead toggles across notifications, email frequency, quiet hours, scheduling and booking permissions.

## Top 10 findings

1. **QR payment-success webhook can never be delivered; payer is charged but `qr_payments` stays `pending` forever.** Checkout sessions are created on the connected Stripe account (`server/routes/qrPayments.js:507`), so Stripe emits `checkout.session.completed` with `event.account` set. The platform webhook rejects it as `webhook_account_mismatch` (`server/controllers/webhookController.js:545-547`) and the connect webhook rejects the event type (`webhookController.js:548-550`; `server/config/stripeWebhookContract.js` does not list it). The QR branch at `webhookController.js:571` is dead for real traffic. Payee totals never update, no notification exists, no sweeper covers stuck rows. The test suite masks it by calling `applyQrPaymentSucceeded` directly (`server/__tests__/qrPayments.test.js:410+`). **Critical.**
2. **Kitchen cancel/refund of a `card`-mode (Stripe Elements) food order issues no Stripe refund; customer paid, no food, money stranded.** The transition-time `payment_status` CASE only flips to `'refunded'` for `wallet_credit`/`oxsteed_credit`/`pay_now` (`server/controllers/foodController.js:4048`); legacy `'card'` is excluded. The automatic Stripe refund branch fires only for `pay_now` (`foodController.js:4253-4263`). Agent console 422s (`refund_payment_mode_unknown`, `server/controllers/agentFoodRefundActions.js:140-146`) and `refundPosCardPayment` only covers POS terminal rows. **Critical.**
3. **Guest `oxsteed_credit` food orders: money is debited at creation, but the DB keeps `payment_status='requires_payment'` forever; on kitchen cancel there is no refund path.** Debit via `spendWithCreditInTransaction` (`server/controllers/foodController.js:3367`) while `initialPaymentStatus` is `'requires_payment'` for guests (`:3006-3009`) and no path ever flips it to `paid`. Refund branch requires `order.customer_id` (`:4222`, NULL for guests) and `payment_status='paid'` (`:4048`). The API even claims `status: 'paid'` (`:3413-3415`) while the column disagrees. **Critical.**
4. **Refresh-token absolute expiry is never enforced server-side.** `refreshToken()` (`server/controllers/authController.js:792-879`) never reads or filters on `sessions.expires_at` (`server/migrations/026_fix_auth_schema.sql:10`) and never calls `jwt.verify` on the refresh JWT, so the 7d `exp` is decorative on this path. An expired session row keeps rotating into fresh rows indefinitely; only cookie Max-Age (client-side) limits it. A stolen refresh token slides forever. **Critical.**
5. **The work agreements records room is non-functional end to end.** All agreement pages double-prefix `/api` against an axios baseURL that already includes it, so every agreement call hits `/api/api/...` and 404s (`client/src/api/axios.js:4` vs `client/src/pages/NewWorkAgreementPage.jsx:29,38,54` and `WorkAgreementPage.jsx:56,71,96,118,130,139,148`). Even with URLs fixed, `create()` posts no `content` and the server 400s (`server/controllers/workAgreementController.js:84`), and `navigate('/agreements/${data.id}')` would land on `/agreements/undefined` since the server returns `{agreement, version}` (`NewWorkAgreementPage.jsx:48-60`). AI drafting 500s on nonexistent `helper_id, customer_id` columns (`workAgreementController.js:538-543` vs `server/migrations/012_phase4_create_jobs.sql:6-7`). **Critical.**
6. **A single super-admin can mark an approved credit settlement `paid` with no rail gate, no second checker, and no Stripe verification.** `transitionSettlement` (`server/services/oxsteedCreditAdminService.js:1589-1698`) contains zero `assertCreditRailEnabled` calls; `POST /super/oxsteed-credit/settlements/:id/status` routes all non-`approved` transitions straight to it (`server/routes/admin.js:438` -> `server/controllers/oxsteedCreditController.js:2238`). The `paid` branch posts the `settlement` journal on a free-text `payment_reference`, even with the rail disabled or frozen, violating the fail-closed-on-freeze rule and the "only the Stripe webhook marks funds settled" principle. **High.**
7. **Direct booking integrity breaks: hold-less path ignores `required_crew_size`, only `crew[0]` is persisted, and quote-flow requests are ownerless.** The hold path reserves full crew (`server/services/directSlotEngine.js:392`) but the hold-less path assigns one least-loaded member (`:673`); the client silently falls back to it when the hold call fails (`client/src/pages/DirectBookSlotPage.jsx:118-122`). `INSERT` persists `assigned_to=crew[0].id` (`directSlotEngine.js:750`) while busy checks filter on `assigned_to` only, so crew members 2..N can be double-booked (`directSlotEngine.js:133`, migration `420_direct_schedule_conflict_guard.sql`). `POST /api/direct/requests` has no auth middleware, so `user_id` is always NULL (`server/routes/direct.js:103`, `server/controllers/quoteRequestsController.js:434`) and `canAccessRequestDetail` 403s the actual customer for every lifecycle action (`server/controllers/directController.js:569-573`) while the thanks page promises they can accept the quote. **High.**
8. **Cross-surface double-booking: the three scheduling silos are mutually blind.** Direct reads `quote_requests` + `direct_slot_holds` only (`directSlotEngine.js:126-165`); helper availability reads `appointments` only (`helperAvailabilityService.js:407-441`); the business engine reads `business_appointments` only (`bookingSlotEngine.js:186-202`). Dispatch roles include `helper`/`helper_pro`, so a Direct-dispatched helper can be booked simultaneously via their own helper appointments with no guard tripping. Helpers' personal blocks/templates/buffers are also invisible to Direct dispatch. **High.**
9. **Didit auto-pass is silently broken: the live webhook never writes `identity_verifications` rows.** The mounted handler `webhookController.diditWebhook` (registered at `server/index.js:301`) writes the `users` table directly in its fallback branch and never inserts `identity_verifications` rows with `provider='didit'`/`status='verified'`/`person_public_id`. The credit rail's auto-pass query finds nothing for anyone verified after migration 671 (`server/services/identityVerificationService.js:113-130`), so everyone falls into manual review. Root cause: the entity-aware handler `diditController.handleWebhook` (the only code creating `duplicate_of` links) is mounted nowhere; the "mounted in index.js" comment at `server/routes/didit.js:16` is stale. Money stays fail-closed, but the feature is dead and the review queue piles up. **High.**
10. **The complaint barrier is unenforced and bypassable everywhere.** `POST /api/support/request` accepts `category='dispute'` with zero agreement/job check (`server/controllers/supportController.js:104-129`). The "Having an issue with this work?" banner renders only on the agreement page (`client/src/pages/WorkAgreementPage.jsx:199-210`), `GET /api/work-agreements/by-job/:jobId` has zero client callers, `DisputeResolutionPage.jsx` contains no agreement check, and warranty-claim filing notifies nobody (`server/controllers/workAgreementController.js:467-487`, `:507-534`). Emile's design (agreement-first complaint barrier) exists only as a banner on a page the jobs flow cannot reach. **High.**

## Per-area findings

### 1. Auth/session

**Flow map.** Password login (`POST /auth/login` -> `login()`, `server/controllers/authController.js:243`): bcrypt + escalating per-account lockout (`:324-338`); non-admin terms + name-matching digital signature (`:369`); TOTP users get a 15-min `mfaToken` instead of a session. 2FA completion (`:520`) with single-use bcrypt-hashed backup codes. Session refresh (`POST /auth/refresh` -> `refreshToken()`, `:792`): cookie-first client with legacy localStorage handoff only on 401 `no_token`, cross-tab Web Locks (`client/src/api/auth.js`, `authRefreshCoordinator.js`), atomic refresh-token consume with `token_reuse` on replay. Logout (`:884`) revokes presented session; Bearer header triggers full revocation. Password reset (`:1408-1453`): hashed single-use tokens, 1h expiry, revokes all sessions + passkeys. Admin passkeys (`server/controllers/passkeyController.js`) and user passkeys (`server/controllers/userPasskeyController.js`, `/api/passkeys`, migrations 643/710). Rate limiters: login 30, session 120, lookup 60 per 15min; strict 10/hr.

**Findings.**
- [Critical] Refresh-token absolute expiry never enforced server-side. `refreshToken()` (`authController.js:792-879`) never reads `sessions.expires_at` (`migrations/026_fix_auth_schema.sql:10`) and never calls `jwt.verify`; the refresh JWT's 7d `exp` (`middleware/auth.js:25`) is decorative. A stolen refresh token rotates forever; only cookie Max-Age (client-side) limits it.
- [High] Admin passkey registration is a dead end. `verifyRegistration` (`passkeyController.js:135`) queries a nonexistent `admin_users` table (no such table/view in 762 migrations) -> every registration 500s. No client page calls `/api/2fa/passkeys/registration/*` (zero callers in `client/src`).
- [High] User passkey sign-in dead-ends for zero-counter authenticators. `userPasskeyController.js:304` rejects `nextCounter <= stored.counter` with no zero-counter exemption, while the admin controller exempts it (`passkeyController.js:260`). iCloud Keychain-style synced passkeys (counter always 0) register fine and can never sign in.
- [Medium] rememberMe (30d) silently degrades to 7 days on first refresh. `refreshToken()` INSERTs an unconditional 7-day session (`authController.js:859`) and drops the `rememberMe` flag when resetting the cookie (`utils/authCookies.js`).
- [Medium] Passkey login skips the per-login digital signature + consent records (`login_agreements`, `user_consents` written by `login()` at `authController.js:441-474` but not by `issueUserSession` at `userPasskeyController.js:247-259`). The `terms_required` 403 branch (`userPasskeyController.js:321`) surfaces as a raw toast with no terms UI (`Login.jsx:117-119`).
- [Medium] Server still emits `accessToken`+`refreshToken` in the JSON body on every session-issuing endpoint (`authController.js:512,687,877`; `userPasskeyController.js:259`; `passkeyController.js:219`); the client provably ignores them (`client/src/api/auth.js:46-52`), so native-only emission would close the exposure for web.
- [Medium] `changePassword`'s "keep current session" logic never fires: nothing ever sets `req.sessionId` (zero assignments in the codebase), so `authController.js:1830` always falls back to the zero UUID and ALL sessions are invalidated; the user is silently logged out right after "Password changed successfully".
- [Low] Cookie-only logout revokes only the current session (other devices stay live); the cookie-clearing Set-Cookie omits the `Secure` attribute used when setting it.
- [Low] Cross-tab passkey ceremony race: `saveChallenge` deletes prior challenges before inserting, so a second tab invalidates the first tab's in-progress ceremony (400 'Passkey authentication expired. Start again.').
- [Low/Info] Duplicate admin passkey auth entry points (`routes/auth.js` `/auth/login/passkey/*` vs `index.js:501` `/api/2fa/passkeys/authentication/*`); only the former is used by the client.
- [Info] Admin sign-in digital-signature field (Emile supplied his full name 2026-10-02) not found in current admin Login page or server code — needs live verification whether planned, reverted, or pending.

**Verified clean:** atomic refresh consume with `token_reuse` reuse-protection; cookie-first refresh with legacy-token handoff; cross-tab refresh lock; authLimiter split; hashed single-use reset tokens with session+passkey revocation; TOTP setup/verify/disable/regenerate with single-use bcrypt-hashed backup codes; OTP hashing/expiry/3-strike lockout; per-account login lockout; all auth routes rate-limited as specified.

## Cross-cutting themes

1. **The double-prefix bug class is systemic, not a one-off.** Pass 1 found it in the work agreements pages (`/api/api/...` 404s). Pass 2 found the same class in the merchant order-center Refund/Split/Merge buttons (`FoodMerchantPage.jsx:702,714,726`) and a correct single-prefix usage nearby (`recordFoodOrderManualPayment`, `api/food.js:316`) proving the pattern is known but not enforced. Any axios-based page that hand-writes `/api/...` paths is suspect.
2. **Audit-log writes are a recurring failure point.** The `admin_audit_log` table has at least three incompatible column dialects in live code: `details` (bid/review moderation, always rolls back), `admin_user_id/entity_type/entity_id/metadata` (admin food refund, throws after money moves; purpose-bound read audit, silently swallowed), and the real `description/before_state/after_state` columns. Business moderation wraps audit writes in bare `catch {}` (deactivate/delete with no record possible), while fraud/incident/reconciliation use fail-closed `throwOnError: true`. The moderation and refund admin flows are broken specifically because of this.
3. **Unwired workers are now corroborated from four angles.** Pass 1: Learn 24h auto-publish and accepted-job expiry depend on `workerMain.js`, which nothing starts. Pass 2: credit-subscription renewals (`workerMain.js:220`), monthly statement auto-issuance and `statement.amended` notifications (scheduler wired only inside workerMain, `statementIssuanceScheduler.js:306`) share the same fate. The production Docker CMD starts only `index.js`.
4. **User-moderation actions do not do what the admin UI promises.** Timed suspensions are permanent (H: is_active never restored); "Restrict" sets `users.is_restricted`, which nothing reads; enforcement-system "full account lock" is enforced on exactly 2 routes (`POST /api/bids`, `POST /api/jobs`) while login/messaging/booking/checkout/food/top-ups keep working; `checkRestrictions('checkout')` and `'all'` types are mounted nowhere; `requireTermsAcceptance` and `requirePlatformApproval` middleware are mounted nowhere.
5. **Identity/verification has three unreconciled flag generations.** Onboarding-era `id_verified`/`background_check_passed` (gates; only ever written by manual super-admin `verifyUser`), Stripe-Identity-era `identity_verified`, and Didit-era `didit_status` (webhooks) — never bridged. Consequences: the paid helper tier2 is permanently unreachable (`saveTier` 403s on `id_verified`); the background-check onboarding step is permanently 403 (`id_submitted` never written); re-submitting ID verification silently revokes an approved `id_verified`.
6. **Settings and notification preferences are largely theater.** 12 notification-preference toggles have no matching notification type ever emitted; the master "Order Updates" email toggle and `email_frequency` off/daily are ignored by the primary realtime path; `sms_notifications`/`push_notifications` masters are honored nowhere; quiet hours cannot be turned on (no code ever sets the enable flag); `allow_scheduling` and `allow_booking` are dead toggles; `allow_live_chat` is client-only.
7. **Intakes and unlaunched surfaces have dead triage loops.** Six template intake systems accept submissions (five via unauthenticated public POSTs, one unthrottled, five accepting caller-supplied `status`) but send no notifications and their triage tabs are unreachable; submitted intakes are invisible to businesses. The unlaunched marketplace is purchasable through ungated cart/checkout/orders endpoints.
8. **Reviews: the business side is untrustworthy and un-notified.** A business owner can unilaterally delete any review on their business (no audit, no notice); two parallel owner-response columns (`response` vs `owner_reply`) mean hub replies are invisible publicly; new-review notification INSERT uses nonexistent columns so it silently never sends; no in-app dispute path exists for job/business/food/tool reviews.

### 14. Session and device management

**Flow map.** `sessions` table: INSERT per login AND per refresh; no sweeper; only account deletion purges. Access tokens are JWTs (15-min) with a denylist enforced in `authenticate`/`optionalAuth`. Logout: Bearer path revokes the access token; cookie path invalidates only the sessions row (copied `oxsteed_access` JWT works until expiry). `revokeAllUserTokens` callers (reset, change-password, set-password, deletions, forceLogout, Bearer logout) also invalidate session rows. Restaurant device tokens (pairing: 48-bit single-use codes, 15-min expiry, hashed tokens); delivery tracking devices (register+list, no pause/revoke/delete). Impersonation JWTs skip the denylist (30-min, ended only by `endImpersonation`).

**Findings.**
- [High] A DB trigger silently enforces single-live-session-per-user (see Top 15 #15). `server/migrations/200_session_fixation_prevention.sql:20-24` (dual-write fix in 716). Framed as fixation prevention, but proper fixation defense rotates the current session; it doesn't kill other devices. Makes all per-session management theater. (Needs live verification whether single-live-session is intended policy.)
- [High] The only session-list endpoint always 500s: `listMySessions` (`GET /admin/settings/me/sessions`) SELECTs `last_used_at` and `user_agent`, which don't exist on `sessions`. The admin UI swallows the error and the Sessions tab permanently lies: "No active sessions." Even fixed, all rows would show NULLs: none of the 11 INSERT sites record device/IP info. `server/controllers/adminSelfSettingsController.js:46-57`; `client/src/pages/AdminUserSettingsPage.jsx:66`.
- [Medium] No user-facing session management at all: no list/revoke/"log out everywhere" for regular users (only the admin pair, one broken).
- [Medium] `revokeMySession` skips the denylist (access JWT valid 15 min post-revoke); `is_current` always false; the self-revoke guard dead (`req.sessionId` never assigned anywhere).
- [Medium] Cookie-only logout never revokes the access token server-side: a copied `oxsteed_access` JWT works until its 15-min expiry. `server/controllers/authController.js:884-962` (revoke only on Bearer path `:922`).
- [Medium] `invalidateUserSessions` (`utils/modeRole.js:174`) skips denylist on role/mode switches (login mode-change, profile, switchRole): old-role JWTs work 15 min post-switch.
- [Medium] Impersonation sessions are immune to all user-level revocation: denylist skipped for impersonation JWTs; force-logout, password reset/change, and suspension of either party never terminate an active impersonation session (30 min). `server/middleware/auth.js:114-139`.
- [Medium] Restaurant device tokens never expire and can't be rotated: `device_token_hash` written once at pair time; disable-then-re-enable resurrects a compromised token. `server/controllers/restaurantAppFlowController.js:2793`.
- [Medium] `sessions` grows unbounded (INSERT per login + per refresh, no sweeper; only account deletion purges at `jobs/scheduledDeletionJob.js:219`).
- [Medium] `delivery_tracking_devices` has register+list but no pause/revoke/delete (CHECK lists 'paused'/'revoked' but nothing writes them): a lost driver phone can't be offboarded.
- [Medium] `refreshToken()` never checks `is_active`/`is_suspended`: suspended users keep rotating into fresh tokens indefinitely. (Extends pass 2.)
- [Low] Expired pairing codes/pending device rows accumulate, no cleanup.
- [Low] `sessions.id` is SERIAL despite migration 200's own comment demanding random IDs.
- [Low] `regenerated_from_session_id`/`parent_session_id` never written.
- [Low] Admins can't see other users' sessions (force-logout is blind, though audited).

**Verified clean:** no session fixation (all 11 issuance sites mint fresh rows); access-token denylist enforced in `authenticate`+`optionalAuth`, fail-closed; every `revokeAllUserTokens` caller also invalidates `sessions` rows; forceLogout audited; device disable locks the token immediately; pairing hygiene sound (48-bit single-use codes, 15-min expiry, hashed tokens); web/mobile push offboarding exists; impersonation end path fail-closed; no trusted-device records exist, so nothing survives password change (passkeys revoked too, per pass 1).
